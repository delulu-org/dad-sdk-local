# dad-sdk-local

The **Delulu Addon Development (DAD) Local SDK** - develop, build, and test
local (native binary) addons for Delulu.

```bash
cargo install --path crates/dad-local-cli
```

> **Local addons are native binaries.** Delulu spawns them as child
> processes and talks to them over newline-delimited JSON-RPC on stdio
> (`protocol_version: "2.0"`). For HTTP addons use
> [`@delulu-addon/dad-sdk`](https://github.com/delulu-org/dad-sdk) instead.

> **Local addons are not open for public publishing.** They execute inside
> the user's own client, so Delulu Core code-signs and verifies every local
> addon before it installs or loads it - only audited, signed, whitelisted
> addons reach users, and there is no third-party submission path to the
> public registry. This SDK is published for inspection, reference, and
> security auditing.

---

## Quick start

```bash
dad-local init my-addon --name "My Addon" --caps direct_stream,meta
cd my-addon
dad-local test
```

`dad-local test` verifies the mandated release profile, runs the clippy

tools itself (via `vswhere`), so PowerShell, cmd, and Git Bash all behave
the same.

## The contract

Every addon implements up to three handlers, gated by the capabilities it
declares in its manifest:

| Capability | Handler | Returns |
|---|---|---|
| `meta` | `getMeta` | `MetaResponse` (imdb_id, imdb_rating, trailers) or `null` |
| `direct_stream` | `getStreams` | `Vec<StreamItem>` - `direct` (plain, or `needs_proxy` + `headers`) |
| `torrent` | `getStreams` | `Vec<StreamItem>` - `torrent` (`info_hash` + required `file_idx`) |
| `subtitle` | `getSubtitles` | `Vec<SubtitleItem>` (vtt, srt, ass, ssa, ttml, dfxp) |

Two envelope methods are generated by `define_local_addon!`: `manifest`
(the binary self-reports; Delulu cross-checks it against the signed
manifest at spawn time) and `healthCheck`.

### The request

```rust
pub struct DadRequest {
    pub tmdb_id: u32,          // TMDB id, e.g. 550
    pub media_type: MediaType, // "movie" | "tv"
    pub s: Option<u32>,        // season - TV only
    pub e: Option<u32>,        // episode - TV only
    pub auth: Option<String>,  // API key from Delulu's vault
}
```

`tmdb_id` must be positive and `s`/`e` are TV-only. Violations come back as
`bad_request` before your handler is ever called. `auth` is the user's key
for this addon, delivered per request and never persisted by the SDK.

### Stream items

- `item_type` is `direct` or `torrent`.
- **Direct**: `stream_url` (HTTPS). Set `needs_proxy: true` plus the exact
  `headers` the host must inject when the origin blocks plain playback.
- **Torrent**: identity is `info_hash` (40 hex chars for v1, 64 for v2) plus
  a required zero-based `file_idx` (`0` for single-file). `stream_url` on a
  torrent is an error.
- `audio_languages` is **required** on every item - `[]` means "unknown".
  A muxed English+Hindi file is one item listing both; never emit the same
  URL twice.
- Optional: `seeders`, `trackers`, `media_format`, `resolution`, `codec`,
  `hdr_format`, `audio_format`, `size_gb`, `subtitles`.
- **Strictness by presence**: a field that does not belong to the item type
  (`info_hash` on a direct stream, `stream_url` on a torrent) is an error
  when present at all - `null` counts as present.

### Meta responses

`MetaResponse { imdb_id, imdb_rating, trailers }` fills only what TMDB does
not already carry. `imdb_rating` must be a number, not a string. Trailers
are HTTPS URLs in preference order - the first is the default.

### Subtitle tracks

`SubtitleItem { id, url, lang_code, language, title, format, provider? }`.
`format` must be one of `vtt`, `srt`, `ass`, `ssa`, `ttml`, `dfxp`. The SDK
checks the container only; it never transcodes - the player renders.

### Errors

Every failure is one closed set of 9 codes in a single shape:

```json
{ "error": "content_unavailable", "error_message": "No streams for this title" }
```

| Code | HTTP | Meaning |
|---|---|---|
| `bad_request` | 400 | Malformed request |
| `method_not_allowed` | 405 | Transport disallows this method |
| `unauthorized` | 401 | Missing or invalid API key |
| `not_found` | 404 | Unknown method or undeclared capability |
| `content_unavailable` | 404 | Title known, no content for it |
| `invalid_response` | 422 | A response failed SDK validation |
| `upstream_unreachable` | 502 | Upstream source could not be reached |
| `rate_limited` | 429 | Caller asked to slow down |
| `internal_error` | 500 | Unexpected addon crash |

`content_unavailable`, `rate_limited`, and an `unauthorized` raised by the
manifest's own api_key gate are **graceful** - the addon works, it just has
nothing to give. `dad-local test` passes those and fails everything else.

## Writing an addon

```rust
#![forbid(unsafe_code)]
use dad_local_runtime::prelude::*;

#[derive(Default)]
struct OpensubsAddon;

impl GetSubtitlesHandler for OpensubsAddon {
    async fn get_subtitles(&self, request: DadRequest) -> Result<Vec<SubtitleItem>, DadError> {
        // request.auth is the user's OpenSubtitles key from Delulu's vault
        // call your upstream, map the results into SubtitleItems
        todo!()
    }
}

dad_local_runtime::define_local_addon! {
    manifest = "manifest.json";   // validated AT COMPILE TIME
    addon = OpensubsAddon;
}
```

Declare `subtitle` in the manifest without the impl - or the impl without
the capability - and **the build fails**. What the HTTP SDK catches at
definition time is a compile error here, enforced in both directions.

### manifest.json

| Field | Required | Notes |
|---|---|---|
| `id` | yes | Reverse-DNS; never rename after publishing |
| `name` | yes | Display name |
| `version` | yes | Strict `major.minor.patch` |
| `type` | yes | Always `local` |
| `protocol_version` | yes | Always `"2.0"` |
| `capabilities` | yes | Any of `direct_stream`, `torrent`, `meta`, `subtitle` |
| `platform_assets` | yes | At least one `{os}-{arch}` entry (see [Platforms](#platforms)) |
| `description`, `publisher` | no | Listing shelf text |
| `logo` | no | HTTPS when set |
| `api_key` | no | `{ required, page_url }` (see below) |
| `signature` | no | `""` while authoring; the publisher tool fills it |

Each `platform_assets` entry carries `download_url` (HTTPS), `binary_name`
(a plain filename - no separators, no `..`), `sha256` (`""` while authoring,
64 hex chars once published), and `entry_command` (arguments Delulu appends
when spawning, default `rpc`).

Unknown fields are rejected outright: `deny_unknown_fields` exists because a
canonically-dropped field would escape the signature. Adding a field
requires a `protocol_version` bump.

### API keys

```json
"api_key": { "required": true, "page_url": "https://example.com/get-key" }
```

When `required` is `true`, the runtime rejects any request arriving without
`auth` **before your handler runs**, returning `unauthorized`. Delulu shows
`page_url` to the user so they can get a key. The SDK never sees, stores, or
validates the key itself - it only checks that one was delivered.

## Building an artifact

```bash
dad-local build
```

The build ends with the artifact path. Hashing and signing stay outside the
SDK: publishing is done by Delulu's internal publisher tool, which pins the
artifact's SHA-256 into `platform_assets[...].sha256` and signs the canonical
manifest payload (the typed manifest, sorted keys, `signature` excluded)
with the team's key. This SDK has no `publish` command by design, because
Delulu Core installs only verified, signed, whitelisted releases - there is
no public local-addon distribution path.

There are two legal manifest states - *authoring* (`sha256` and
`signature` are `""`) and *release* (both filled). Delulu installs only
release state.

## CLI reference

| Command | What it does |
|---|---|
| `dad-local init <dir>` | Scaffold a crate: `Cargo.toml`, `manifest.json`, `src/main.rs`, `README.md`, `clippy.toml` |
| `dad-local validate [dir]` | Check `manifest.json` against the contract |
| `dad-local build [dir]` | Mandated profile check, clippy gate, portability check, `--release` build |
| `dad-local dev [dir]` | Debug build plus fixture probes, for iteration (`--fixtures N`) |
| `dad-local test [dir]` | The release gate: release build with the clippy gate, every fixture x every capability (`--key` to test the authenticated path) |

Common flags: `--target <triple>` builds for a specific target,
`--skip-clippy` bypasses the lint gate, `--skip-portability` bypasses the
cross-target check (both loudly warned), `--sdk-path <dir>` points `init`
at this workspace.

`init` writes path dependencies on `dad-local-core` and
`dad-local-runtime`. They resolve from the CLI's own build location by
default, or from `--sdk-path`.

The addon's `Cargo.toml` must carry the mandated profile - `build` and
`test` refuse to run without it:

```toml
[profile.release]
opt-level = 3
lto = true
codegen-units = 1
strip = true
```

`panic` must stay `unwind`: the runtime catches handler panics and turns
them into `internal_error`, which `abort` would make impossible.

`build` and `test` then run a clippy gate -
`cargo clippy -- -D warnings -D clippy::disallowed_methods`. The
scaffolded `clippy.toml` denies `std::fs` reads and writes,
`std::process::Command`, `std::env::var(_os)`, and
`std::net::TcpStream::connect`: a local addon is a stateless resolver, so
files, processes, environment, and raw sockets are host concerns. Only the
addon crate is linted - path dependencies are compiled, never linted - so
the gate can only ever fail on your code.

## Platforms

`platform_assets` is keyed `{os}-{arch}`. These seven keys map to real
target triples, and `dad-local build` runs `cargo check` against each one
the manifest declares - so a `#[cfg(windows)]` shortcut that breaks other
targets fails the build:

| Key | Target triple |
|---|---|
| `windows-x64` | `x86_64-pc-windows-msvc` |
| `windows-x86` | `i686-pc-windows-msvc` |
| `windows-arm64` | `aarch64-pc-windows-msvc` |
| `linux-x64` | `x86_64-unknown-linux-gnu` |
| `linux-arm64` | `aarch64-unknown-linux-gnu` |
| `macos-x64` | `x86_64-apple-darwin` |
| `macos-arm64` | `aarch64-apple-darwin` |

Unknown keys fail loudly rather than being skipped. Cross-compiling needs
the target installed (`rustup target add <triple>`) plus a linker for it -
building macOS binaries from Windows or Linux needs the matching toolchain.

The SDK crates themselves carry no OS-specific code: no `cfg(windows)`, no
`std::os::*`, no platform crates. The CLI runs on Windows, macOS, and Linux.

## Package layout

| Crate | Role |
|---|---|
| `dad-local-core` | The contract: manifest types and validator, request/stream/meta/subtitle validators, the 9-code error model, canonical signing payload. Pure `serde`, zero I/O, zero crypto. |
| `dad-local-toolchain` | Drives cargo through the machine's real build environment (the `vcvarsall` environment on Windows), so the CLI and the SDK's own compile-contract tests build addons identically. |
| `dad-local-macros` | `define_local_addon!` - compile-time manifest validation and capability-gated handler bounds. |
| `dad-local-runtime` | What runs inside the addon: owns stdin/stdout, enforces the RPC envelope, the api_key gate, panic containment, and response validation before anything leaves the process. |
| `dad-local-cli` | Author-side tooling: `init`, `validate`, `build`, `dev`, `test`. |

`reference/demo_open` and `reference/demo_gated` are complete addons driven
end-to-end by the runtime's subprocess tests.
